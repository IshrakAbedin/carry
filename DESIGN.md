# carry — Design Document

**carry** is a C/C++ project manager that behaves like Rust's **Cargo**: a single small CLI,
a project manifest, and deterministic build/test/run commands. Under the hood it drives
**CMake** (configuration), **Conan 2** (dependencies), **Ninja** (build), and **g++** (compiler).

This document is the stable reference. **Do not rewrite silently** — architecture changes are
appended to `## Decisions` with a date.

---

## 1. Vision

A C/C++ developer should be able to:

```
carry new myapp          # scaffold
carry add fmt            # add a dependency
carry build --release    # compile
carry run                # build + run
carry test               # build + run tests
carry clean              # wipe build/
```

…without ever touching CMakeLists.txt or conanfile.txt by hand. The manifest (`CARRY.toml`)
is the single source of truth; everything else is generated.

## 2. Command surface (MVP)

| Command | Behavior |
|---|---|
| `carry new <name> [--lib]` | Create `./<name>/` scaffold (bin by default; `--lib` adds a library target) |
| `carry init` | Turn the current dir into a carry project (name from dir; errors if CARRY.toml exists) |
| `carry build [--release]` | Regenerate → conan install → cmake configure → ninja build. Default Debug, `--release` = Release |
| `carry run [args]...` | `build` (Debug) then exec `build/bin/<name> [args]...` |
| `carry test` | `build` (Debug) then `ctest --test-dir build --output-on-failure` |
| `carry clean` | Remove `build/` |
| `carry add <pkg>[@<version>]` | Add/update a dependency in CARRY.toml (toml_edit, preserves formatting) |
| `carry remove <pkg>` | Remove a dependency from CARRY.toml |
| `carry --version`, `--help` | clap-provided |

Non-commands for MVP (future): workspace, publish, lockfile management, custom cmake hooks,
cross-compilation, MSVC/Clang.

## 3. Generated project layout

```
<project>/
├── CARRY.toml          # manifest — user-owned, single source of truth
├── conanfile.txt       # generated by carry
├── CMakeLists.txt      # generated by carry
├── .gitignore          # written by `carry new` (build/, CMakeUserPresets.json)
├── src/
│   ├── main.cpp        # if type includes bin
│   └── lib.cpp         # if type includes lib
├── include/<name>/
│   └── <name>.hpp      # if type includes lib
└── tests/
    └── test_main.cpp   # trivial assert-based test binary (no framework), always created
```

Conventions:
- Build dir: `build/` at project root (gitignored). Binaries land in `build/bin/<name>`.
- Library target name: `<name>_lib` (avoids clashing with the executable name).
- Test target: `test_<name>`, registered with CTest as `<name>_tests`.
- Dependency CMake target: `<pkg>::<pkg>` (Conan 2 default); exotic packages needing a custom
  mapping are future work (explicit override key in the manifest).

## 4. CARRY.toml schema

```toml
[package]
name = "demo"          # required; [a-z0-9_][a-z0-9_-]*
version = "0.1.0"      # required; semver string
type = "bin"           # "bin" | "lib" | "both"   (default "bin")

[build]
cpp_std = "c++23"      # default "c++23"
c_std   = "c11"        # default "c11"

[dependencies]
fmt = "10.2.1"         # pkg = version ("10.2.1") or range (">=10")
```

Version mapping to Conan refs:
- plain version `10.2.1` → `fmt/10.2.1`
- range `>=10` → `fmt/[>=10]`
- bare `fmt` (no version) → `fmt/[>=0]` — "any version"; a bare `fmt/*` is
  **not** a resolvable require in Conan 2 (D11)

Standard mapping to Conan settings (D12):
- `cpp_std` `c++23` → `-s compiler.cppstd=gnu23` (GNU dialect for the pinned
  GCC, D6) — passed to `conan install` so the dependency graph is resolved
  with the standard the generated CMakeLists compiles with
- `c_std` — project-local (Conan has no C-std setting)

## 5. Generated files

### conanfile.txt (generated)

```
[requires]
fmt/10.2.1

[generators]
CMakeDeps
CMakeToolchain
```

### CMakeLists.txt (generated)

```cmake
cmake_minimum_required(VERSION 3.21)
project(demo VERSION 0.1.0 LANGUAGES C CXX)

set(CMAKE_C_STANDARD 11)
set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_RUNTIME_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/bin)

find_package(fmt REQUIRED)          # one per dependency

add_library(demo_lib STATIC src/lib.cpp)     # only if lib
target_include_directories(demo_lib PUBLIC include)
target_link_libraries(demo_lib PUBLIC fmt::fmt)   # deps PUBLIC (D10)

add_executable(demo src/main.cpp)            # only if bin
target_link_libraries(demo PRIVATE demo_lib fmt::fmt)   # lib first, then deps
target_include_directories(demo PRIVATE include)

enable_testing()
add_executable(test_demo tests/test_main.cpp)
target_link_libraries(test_demo PRIVATE demo_lib fmt::fmt)   # lib (if present), then deps — never the exe (D9)
add_test(NAME demo_tests COMMAND test_demo)
```

Regeneration rule: on every `build`/`run`/`test`, carry renders both files in memory and
rewrites them **iff content differs** from what is on disk. No state file needed.

## 6. Build pipeline (`carry build`)

Run from the project root (carry walks up from cwd to find `CARRY.toml`; error if none).

1. Parse `CARRY.toml` → `Manifest` (serde).
2. Render `conanfile.txt` + `CMakeLists.txt`; write if changed.
3. `conan install . --output-folder=build --build=missing
      -s build_type=<Debug|Release> -s compiler.cppstd=<gnuNN>`
   (cppstd derived from the manifest's `cpp_std`, D12)
   → writes `build/conan_toolchain.cmake` + CMakeDeps configs into `build/`.
4. `cmake -S . -B build -G Ninja \
      -DCMAKE_TOOLCHAIN_FILE=build/conan_toolchain.cmake \
      -DCMAKE_BUILD_TYPE=<Debug|Release> \
      -DCMAKE_C_COMPILER=gcc -DCMAKE_CXX_COMPILER=g++`
   Always run (reconfigure is cheap; keeps conan updates in sync).
5. `cmake --build build`

`carry test` adds: `ctest --test-dir build --output-on-failure`
`carry run` adds: exec `build/bin/<name> <args...>`, propagating exit code.

Tool invocation rules:
- Stream child stdout/stderr directly to the terminal (never buffer build output).
- On failure: print `error: <tool> failed with exit N` and the command that was run; exit non-zero.
- Missing tool (not on PATH): `error: required tool 'conan' not found on PATH`.
- `--verbose` (global flag): print each command before running it.

## 7. Rust implementation structure

```
Cargo.toml          # bin "carry"; deps: clap(derive), serde(derive), toml, toml_edit, anyhow
src/
├── main.rs         # clap CLI, command dispatch, exit codes, --verbose
├── manifest.rs     # Manifest struct (serde), load/save via toml_edit, version-ref mapping
├── project.rs      # find_project_root() (walk up for CARRY.toml), path helpers
├── template.rs     # `carry new`/`init` scaffold contents (main.cpp, lib.cpp, hpp, test_main.cpp, .gitignore)
├── generate.rs     # Manifest → conanfile.txt / CMakeLists.txt render + write-if-changed
└── build.rs        # run() helper, build()/test()/run()/clean() pipelines
tests/
├── manifest_test.rs   # parse round-trips, version mapping, validation
├── generate_test.rs   # rendered file contents, idempotence (write-if-changed)
└── e2e.rs             # spawn the built binary: new→build→run→test→add→clean in a temp dir
```

Testing policy:
- Unit tests for manifest + generator (fast, no toolchain needed).
- Integration tests that shell out to the real `carry` binary (env `CARRY_BIN` or cargo target path)
  in `tempfile` dirs. E2E tests requiring Conan Center network are marked `#[ignore]`
  and listed in T007.

## 8. Error handling & UX

- `anyhow::Result` end-to-end; `#[derive(Parser)]` clap with subcommands.
- Errors prefixed `error: `; usage hints after `help: ` when obvious.
- Exit codes: 0 ok; 1 carry error; 101 propagated child (build/test/run) exit code for run.
- No colors in MVP (plain text, grep-friendly).

## 9. Non-goals (MVP)

No lockfile (Conan's own cache resolution is enough for now), no registry/publish, no
workspace/multi-package, no custom-CMake escape hatch, no non-GCC compilers, no Windows paths,
no Conan profile management (use the `default` profile).

## 10. Future work (post-MVP, ordered)

1. `conan lock` support for reproducible builds (`carry freeze` / `carry update`).
2. `extra.cmake` hook: optional user file `include()`d at the end of generated CMakeLists.
3. Dependency target-name override (`[dependencies.fmt] target = "..."` table form).
4. Colors + `--quiet`.
5. `carry update` (refresh versions), `carry metadata` (print resolved graph).
6. MSVC/Clang via `cc`/`cxx` keys in `[build]`.

## Decisions

- **D1 (2026-09-17)** — Implement carry in **Rust**: user is Rust-fluent, cargo is available,
  fast testable CLI, `toml_edit` for manifest editing. The *managed* projects are C/C++.
- **D2 (2026-09-17)** — **Conan 2 with `conanfile.txt`** (not `.py`): text format is trivial to
  generate and diff; script logic not needed for MVP.
- **D3 (2026-09-17)** — **Manifest is the single source of truth**: carry regenerates
  `conanfile.txt` and `CMakeLists.txt` on every build (write-if-changed). Users do not edit
  generated files; future `extra.cmake` hook for escape hatches.
- **D4 (2026-09-17)** — Build dir is `build/`; **Debug is the default** (fastest feedback,
  matches CMake convention); `--release` opt-in.
- **D5 (2026-09-17)** — Configure with `-DCMAKE_TOOLCHAIN_FILE=build/conan_toolchain.cmake`
  (CMakeToolchain sets prefix/module paths itself — no manual `CMAKE_PREFIX_PATH`).
- **D6 (2026-09-17)** — Pin `CMAKE_C_COMPILER=gcc` / `CMAKE_CXX_COMPILER=g++` explicitly
  (deterministic compiler, matches the user's toolchain).
- **D7 (2026-09-17)** — **Repo-as-memory**: `BOOTSTRAP.md` (protocol) + `STATE.md` (current
  state) + `TASKS.md` (backlog) + `tasks/` (self-contained task prompts) + `results/`
  (per-task outcomes) + `ISSUES.md` + `SESSION_LOG.md` + `prompts/` (paste-ready session
  prompts). Every session follows the protocol in BOOTSTRAP.md and ends by recording.
- **D8 (2026-09-17)** — E2E tests needing Conan Center network are `#[ignore]`d so the
  default test suite is hermetic; T007 exercises them manually and records the result.
- **D9 (2026-09-21)** — The generated test target links the **library** target (when
  present) plus the dependencies, and **never the executable** target. T003 found the
  §5 example line `target_link_libraries(test_demo PRIVATE demo ...)` does not
  configure: CMake 4 rejects linking an EXECUTABLE target into another target, and
  even with `ENABLE_EXPORTS` it would duplicate `main` (exe's `src/main.cpp` vs the
  test's `test_main.cpp`). The §5 example line was updated accordingly.
- **D10 (2026-09-21)** — The generated **library** target links the project's
  dependencies as **PUBLIC**. T007 found that without this, a `#include <fmt/format.h>`
  in `src/lib.cpp` silently resolves to the *system* fmt headers (when one is
  installed) while the link line uses Conan's `libfmt.a` — a compile that "works"
  but fails at link time on mismatched inline-namespace symbols (`fmt::v12` vs
  `fmt::v10`). PUBLIC (rather than PRIVATE) is the safer default for a generated
  library: consumers of `<name>_lib` get the dependency's includes and link
  transitively. The exe/test keep their explicit dependency link lists (needed for
  bin-only projects; harmless redundancy for `both`). The §5 example line was
  updated accordingly.
- **D11 (2026-09-21)** — A bare `pkg` (no version) maps to the range
  `pkg/[>=0]`, **not** the literal `pkg/*` the §4 table originally specified.
  T007 found Conan 2.32.0 rejects a bare `*` as a require: `conan install`
  fails with "Package 'fmt/*' not resolved" even when `fmt/10.2.1` sits in the
  local cache (the `*` is looked up literally, and the remote 404s it), while
  `fmt/[>=0]` and `fmt/[>=10]` resolve fine (highest available version, cache
  preferred). Related: `carry add fmt@` (trailing `@`, empty version) is
  rejected with a `help:` hint — the `@` promises a version; dropping it is
  how you ask for "any".
- **D12 (2026-09-21)** — `conan install` receives
  `-s compiler.cppstd=<gnuNN>` derived from the manifest's `cpp_std`
  (`c++23` → `gnu23`), overriding the profile's `cppstd` for the host
  context. T009 (a glaze demo build) found the profile's `cppstd` (gnu20)
  and the generated `CMakeLists.txt`'s `CMAKE_CXX_STANDARD 23` had diverged
  since T004: benign for fmt (which never checks), but a hard error for
  recipes that validate the standard — glaze/8.3.0 fails `conan install`
  with `Invalid: Current cppstd (gnu20) is lower than the required C++
  standard (23)`. The manifest is the single source of truth for the
  standard (D3), so the graph must be resolved with it; the profile still
  governs everything else (compiler, libcxx, arch). The `gnu` prefix
  assumes the pinned GCC (D6) — MSVC/Clang support (§10.6) must revisit the
  mapping. Unqualified `-s` targets the host context only; build-context
  tool requirements keep the profile's standard (prebuilt in practice).
  Side benefit: conan's toolchain now emits the same standard as the
  generated CMakeLists, so the "modified to 23" configure warning is gone.
